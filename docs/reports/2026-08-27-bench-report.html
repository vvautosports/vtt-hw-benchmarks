Local model benchmark results, and how to read them

Which local models pass our tests, how fast they run, and exactly what "pass" means. All numbers below come from committed runs with full transcripts in the vtt-hw-benchmarks repo.

What the benchmark actually is

Every model gets the same three tasks, sent one at a time through the same API a real app would use (identical settings for every model: sampling fixed, seed fixed, 8,192-token output limit). A script then checks each answer against mechanical pass criteria — no human judging, no "AI grading AI." A result is either verifiably right or it isn't, and re-running the check always gives the same grade.

Task 1 · Reasoning

A multi-step word problem: three delivery trucks return to a warehouse every 12, 18, and 30 minutes — how many times between 6 AM and 6 PM do all three arrive together? The model must show its work, then state the count on its own line as ANSWER: <n>.

Pass: the answer line exists and the number is exactly 5 (the provably correct count).
Task 2 · Coding

Write a Python function that parses a range string like "1-3,5,7-9" into [1,2,3,5,7,8,9] — with rules: ignore stray whitespace, reject reversed ranges like "9-7" with a ValueError, return [] for empty input — and include a doctest block (embedded, runnable examples) covering at least 5 cases.

Pass: the reply contains a real function with ≥ 5 doctest examples and handles the ValueError requirement.
Task 3 · Summarization

Summarize a ~430-word technical passage (about speculative decoding) as exactly 5 bullet points followed by a one-sentence TL;DR — no invented claims. This tests instruction-following under a strict format, which is where degrading models slip first.

Pass: exactly 5 bullets + a labeled TL;DR line, both present.

The three numbers we record per task

Speed — tokens/secHow fast the model writes. A token ≈ ¾ of a word. On this hardware, ~30 tok/s feels responsive for chat; 50+ is fast; under 15 you're waiting on it.
Output tokensHow much the model wrote (thinking included) to reach its answer. Lower is better at equal quality — a model that needs 3× the tokens is 3× slower in practice even at the same tok/s.
Pass / failThe mechanical check above. We report per-task marks, not an averaged score — a model that fails coding but aces summaries is a different tool than the reverse, and an average would hide that.

Why some earlier numbers changed

While benchmarking we found three defects in the serving stack (not the models) that had been quietly distorting results. Each is now fixed or worked around, and affected runs were re-measured — that's why some models "got better" today:

1 · A memory setting was corrupting model output

The serving software enables a special unified-memory mode on this hardware; combined with the current runtime it garbles what models compute — from subtle formatting loss all the way to endless gibberish. Proven by asking a model to continue "one, two, three," and getting //////// back. Disabling the mode fixed every symptom, and it's now off permanently on both machines. This alone had made two good models look broken.

2 · The server was leaking one request's context into the next

Models sometimes "remembered" things from a previous, unrelated request — e.g. claiming they'd already written the code, or answering the prior question. Verified by reordering tests and by giving each test a freshly started server: on fresh servers, every affected model passed. All grading now uses a fresh server per task.

3 · The server was silently giving models tools mid-benchmark

The serving software attaches web-search and code-execution tools to every request by default (~1,200 hidden tokens per request), and one model actually tried to run its answer instead of writing it. Benchmarks now explicitly disable server tools; pass/fail grades were unaffected, but speed comparisons before/after this fix aren't apples-to-apples.

Compression levels: is a smaller download as good?

Models ship at different quantization (compression) levels — smaller files, slightly lower fidelity. We ran Qwen3.8-Flash-Next at three levels to see what compression actually costs:

VersionDisk sizeAll 3 tasksSpeed (tok/s)Words written to finishReal wait, whole battery
Q4 — standard104 GBpass14–18lowest113 s ← fastest
IQ4 — lighter94 GBpass15–20higher338 s
Q2 — heavy compression79 GBpass20–253× the standard272 s

The counterintuitive result: heavier compression generates tokens faster (less data to move per token on this memory-limited hardware) but the model becomes more long-winded — it needs far more words to reach the same answer, so you actually wait longer. Compression damage shows up as rambling before it shows up as wrong answers. Conclusion: keep the standard Q4 version for serving; the 79 GB version is a validated fallback when disk/memory demands it.

Trust notes

  • One prompt set, one seed. This battery is a consistent yardstick, not a statistical survey — a single-cell pass/fail flip (like the two near-misses above) is within its noise floor. Trends and big gaps are the signal.
  • "Cleanest run" means: measured after all three serving fixes, with a fresh server per task and tools disabled where available; otherwise the best-controlled earlier run, noted in the repo manifests.
  • Every row is reproducible: the exact prompts, raw model outputs, and grading script are committed alongside each run in results/sweeps/.
  • Numbers are from one machine (Framework Desktop, Strix Halo). The Windows machine (G1a) gets its own pass later — OS is itself a test axis.
